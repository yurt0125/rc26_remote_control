# LoRa 长期断连排查与恢复方案

> 日期：2026-06-28  
> 当前代码分支：`develop`  
> 范围：遥控器 STM32F4、接收机 STM32H7、两端 LoRa 模块与机器人业务层

## 1. 现象与初步结论

已知现象：

- 偶发通信断连，遥控器下发指令不能被机器人接收。
- 长期断连时，遥控器连接 LoRa 的 TX、RX 串口仍有数据。
- 机器人本体 `rx_cnt` 不增加，无法控制。
- 重启遥控器整机电源后恢复。
- 在 MCU 不重启的情况下，仅将 LoRa 模块断电后重新上电，通信链路也能恢复。
- 断连后仅执行软件重启仍不能恢复通信。

“遥控器串口仍有数据”只能证明 MCU 与本机 LoRa 之间存在 UART 活动，不能证明：

- 字节构成完整且 CRC 正确的控制帧；
- LoRa 模块真正完成空中发送；
- 两端模块仍处于相同信道、地址和模式；
- 接收机模块向 H7 输出了数据；
- H7 DMA、FIFO、解析任务成功处理了数据。

“软件重启不能恢复，而 LoRa 模块断电重启可以恢复”构成了明确的对照证据。它说明清理 MCU
软件状态、任务或普通 UART/DMA 状态不足以解除故障，故障高度集中在 LoRa 模块自身状态、模块
供电/上电复位和模式脚。当前嫌疑优先级调整为：

1. LoRa 模块内部状态机卡死、射频收发状态异常或模块固件异常；
2. 模块供电瞬态、欠压、纹波、RESET 或模式脚受到干扰；
3. 模块异常后 AUX 仍表现为可发送，导致 MCU 误认为链路正常；
4. MCU 与 LoRa AUX、UART 状态机失步，且模块重新上电后重新同步；
5. UART 持续发送，但模块不再进行有效空中发送。

这项证据大幅降低 MCU 业务软件为根因的概率，但仍不能完全排除 MCU 与模块接口状态问题：模块
断电重启会改变 AUX 和 UART 电平，可能间接触发 MCU 状态重新同步。因此仍需记录模块断电前后
AUX、DMA、`tx_busy` 和计数器，确认真正的恢复触发点。

## 2. `develop` 分支当前基线

静态检查确认：

- 两端已有 TX busy 超时恢复、`HAL_UART_AbortTransmit()` 和独立
  `tx_timeout_recovery_cnt`。
- 遥控器已有全局调试快照 `g_comm_tx_timeout_recovery_cnt`。
- 接收机 LoRa 已在初始化后关闭 DMA HT，并在回调中过滤
  `HAL_UART_RXEVENT_HT`。
- 公共 `BSP_USB_UART_Driver.cpp` 未修改。
- 接收机 `rx_dma_buffer` 已按 32 字节对齐。
- 接收机读取 RX DMA 缓冲区前尚未实际执行 D-Cache invalidate；源码注释称由其他位置处理，
  但当前 LoRa 回调链没有确认到对应操作，这是重点核查项。
- 两端 `COMM_TX_BUSY_TIMEOUT_MS` 当前均为 `50U`，与此前约定的 100 ms 不一致。

测试前必须记录 Git 提交号、两端固件编译时间、LoRa 型号/固件/配置，确认烧录文件确实来自当前源码。

## 3. 必须增加的分层观测量

计数器建议使用 `volatile uint32_t`，只递增不自动清零，并记录对应的最后发生时间。

### 3.1 遥控器发送链路

| 变量 | 递增位置 | 能证明什么 |
|---|---|---|
| `joy_frame_build_cnt` | 控制帧构造完成 | MCU 是否持续产生指令 |
| `tx_frame_enqueue_ok_cnt` | 完整帧原子入队成功 | 控制帧是否完整进入 FIFO |
| `tx_frame_drop_cnt` | FIFO 空间不足，整帧丢弃 | 是否发生发送拥塞 |
| `uart_tx_start_ok_cnt` | TX DMA 返回 `HAL_OK` | HAL 接受 DMA 请求 |
| `uart_tx_start_fail_cnt` | TX DMA 启动失败 | UART/DMA 是否异常 |
| `uart_tx_cplt_cnt` | LoRa TX DMA 完成回调 | 字节是否真正离开 MCU UART |
| `aux_rise_cnt` | AUX 上升沿 | 模块是否从忙转为空闲 |
| `aux_fall_cnt` | AUX 下降沿 | 模块是否进入忙状态 |
| `tx_busy_timeout_cnt` | 超时恢复分支 | MCU 与模块状态是否失步 |
| `last_tx_tick` | 每次 DMA 启动/完成 | 发送停止的具体时刻 |

同时观察：`tx_busy`、AUX 当前电平、TX FIFO 占用量、UART `gState`、DMA State、UART ErrorCode。

当前 `tx_cnt` 在 `HAL_UART_Transmit_DMA()==HAL_OK` 后增长，只表示 DMA 启动成功，
不能证明 DMA 完成或空中发送成功。

### 3.2 接收机接收链路

| 变量 | 递增位置 | 能证明什么 |
|---|---|---|
| `uart_rx_event_cnt` | 每次 RxEvent 入口 | 是否存在 UART/DMA 事件 |
| `uart_rx_idle_cnt` | IDLE 事件 | 模块是否输出数据批次 |
| `uart_rx_ht_cnt` | HT 事件 | HT 是否仍被触发 |
| `uart_rx_tc_cnt` | TC 事件 | DMA 缓冲区是否收满 |
| `uart_rx_byte_cnt` | 实际写入 RX FIFO | H7 收到的原始字节量 |
| `rx_fifo_drop_cnt` | FIFO 无空间 | 软件是否消费不及时 |
| `header_error_cnt` | 帧头搜索失败 | 数据是否错位/乱码 |
| `tail_error_cnt` | 帧尾错误 | 是否存在残帧 |
| `rx_crc_error_cnt` | CRC 错误 | 数据完整性是否异常 |
| `joystick_frame_count` | 控制帧完整通过校验 | 真正有效的遥控链路计数 |
| `last_valid_rx_tick` | 有效控制帧到达 | 失联起始时间 |

接收机 `rx_cnt` 只在完整帧解析成功后增加。它停止可能意味着完全没有字节，也可能意味着持续收到坏帧。
必须结合原始事件、字节、CRC 和 FIFO 计数判断。

## 4. 故障现场操作流程

断连后不要立即复位，依次执行：

1. 暂停调试器，记录两端所有计数器、时间戳、AUX 电平、UART/DMA 状态和错误码。
2. 恢复运行，确认哪些计数器继续增加，哪些已经停止。
3. 逻辑分析仪同时抓遥控器 LoRa UART_TX、UART_RX、AUX，至少 2 秒。
4. 同时抓接收机 LoRa UART_TX、UART_RX、AUX。
5. 导出遥控器 UART_TX 原始字节，验证帧头、帧尾、长度、CRC以及内容是否随摇杆变化。
6. 测量两端 LoRa 供电，特别关注发射瞬间压降、纹波、RESET 和模式脚。
7. 记录距离、天线连接、温度、附近同频设备及发生时间。

“串口有波形”不是通过判据；必须确认波特率正确、帧完整、CRC正确且数据持续变化。

## 5. 单独复位隔离实验

每项实验都应重新复现故障后再执行，一次只改变一个对象：

1. 仅清理遥控器 Comm 软件状态，不复位 UART 和 LoRa 模块。
2. 仅 Abort 并重新初始化遥控器 LoRa UART/DMA，不断开模块电源。
3. 仅硬件复位或断电重启遥控器 LoRa 模块，遥控器 MCU 保持运行。
4. 仅重启接收机 LoRa UART/DMA。
5. 仅硬件复位接收机 LoRa 模块。
6. 最后才重启遥控器整机，作为对照。

判断：

- 只清软件状态恢复：重点查 `tx_busy`、任务通知、FIFO和并发。
- 只重启 UART/DMA 恢复：重点查 HAL UART/DMA 状态机。
- 只重启遥控器 LoRa 模块恢复：基本锁定模块内部状态、模式脚或供电。
- 只重启接收机 LoRa 模块恢复：重点查接收模块。
- 只有遥控器整机重启恢复：继续分别检查 MCU 初始化时序和模块上电时序。

如果 LoRa 没有独立 RESET 或电源使能脚，建议临时飞线增加；否则无法区分遥控器 MCU 与模块故障。

### 5.1 已完成的隔离结论

已验证“LoRa 模块单独断电再上电后链路恢复”。后续不必再把遥控器整机重启作为主要恢复方式，
应重点比较以下三个动作：

1. 仅拉动 LoRa RESET，电源不断；
2. 仅切断 LoRa 电源后重新上电；
3. UART/DMA 软件重初始化，但 LoRa 模块不复位。

目前已确认软件重启不能恢复，可将“单纯软件状态异常”降为次要嫌疑。下一步最有价值的是比较
RESET 与完整掉电：若 RESET 和掉电均能恢复，可以实现自动硬复位；若只有完整掉电能恢复，应
重点检查 RESET 脉宽、复位脚连接、模块上电复位电路，以及模块电源是否真正降到规定阈值以下。

## 6. 计数器判定树

### 6.1 `joy_frame_build_cnt` 停止

控制帧生成任务停止，或构帧逻辑被 `tx_busy` 阻塞。当前遥控器只有在 `tx_busy==0` 时才生成摇杆帧，
应重点验证超时期间是否因此产生较长控制帧空窗。

### 6.2 构帧增长，但 DMA 启动不增长

检查 FIFO、`tx_busy`、AUX、任务通知和 HAL 状态。确认超时恢复是否执行，以及恢复后是否重新触发发送。

### 6.3 DMA 启动和完成增长，但 AUX 长期不变化

MCU 已完成 UART 发送，LoRa 模块没有正常处理。优先检查模块忙状态、模式脚、供电和模块内部卡死。

### 6.4 遥控器发送链增长，接收机 `uart_rx_event_cnt==0`

问题位于空中链路或接收模块之前。核对信道、地址、空中速率、工作模式和天线，并优先执行模块单独复位。

### 6.5 接收机 UART 事件增长，但 `rx_cnt` 不增长

- CRC 增长：检查 H7 D-Cache、DMA HT重复、UART误码。
- FIFO drop 增长：解析任务不及时或临界区过长。
- 帧头/帧尾错误增长：检查残帧、逐字节丢弃、DMA重启窗口。
- 原始字节增长但所有解析计数不变：检查解析任务是否仍被调度。

### 6.6 接收机 LoRa RX 引脚完全无波形，遥控器重启后立即恢复

最符合遥控器 LoRa 模块卡死、误入配置态或供电异常。重点检查遥控器模块 RESET、模式脚、AUX 和供电。

## 7. 推荐修复顺序

以下是排查后应按风险从低到高实施的代码改动，本文件不直接修改源码：

1. 给 LoRa 增加 MCU 可控的 RESET 或电源使能，并确认复位/掉电时序符合模块手册。
2. 增加双向心跳或控制帧确认；UART DMA 完成不能作为空中链路正常的依据。
3. 连续多个心跳周期没有收到对端新帧时，先保存故障快照，再执行模块硬件复位和参数重配置。
4. 将两端 TX busy 超时统一回约定的 100 ms，并验证计数器。
5. 让遥控器周期构造最新控制状态不受 `tx_busy` 限制；拥塞时丢弃旧控制帧，只保留最新帧。
6. 所有 TX FIFO 写入先检查整帧空间，整帧原子入队；禁止只丢部分字节形成残帧。
7. 保留接收机 HT 关闭和 HT 事件过滤。
8. 在接收机 LoRa RX DMA 数据被 CPU 读取前执行正确的 D-Cache invalidate；地址与长度按 32 字节向外取整。
9. 增加控制帧序号，接收端统计跳号、重复和最大连续丢帧。
10. 实现分级恢复：保存现场 → 尝试硬件 RESET → 必要时切断 LoRa 电源 → 等待稳定上电 →
    重新配置模块 → 清 UART/DMA 状态 → 恢复通信。已知无效的软件重启不应被无限重复执行。

任何恢复期间，机器人必须保持失联安全状态，不能继续执行最后一次运动指令。

## 8. 压力与故障注入

- 连续运行 8 小时，再进行 24 小时测试。
- 高频操作全部按键和摇杆，制造最大负载。
- 屏蔽 AUX 上升沿超过 100 ms，验证超时恢复。
- 在可控环境下中断并恢复空中链路，验证自动恢复。
- 单独拉低模块 RESET，验证模块重新初始化。
- 对模块电源施加受控压降，检查欠压后的状态。
- 延迟接收解析任务，验证 FIFO 和整帧丢弃策略。
- 注入 CRC 错帧，确认坏帧不会刷新链路存活时间。

每次测试记录首次故障时间、全部计数器差值、恢复动作、恢复耗时和是否需要人工断电。

## 9. 问题解决判据

- 24 小时压力测试无人工断电才能恢复的长期断连。
- 干扰解除后能在规定时间内自动恢复。
- TX busy 超时偶发增加不会导致永久失联。
- 能明确区分“没有原始字节”“收到坏帧”和“收到有效帧”。
- 能通过帧序号量化丢帧率和最长连续丢帧。
- 模块复位期间机器人进入安全状态，恢复后只使用最新控制帧。
- 每次结果都有固定固件版本和故障现场快照。

## 10. 首轮执行清单

1. 固定 `develop` 当前提交和两端固件版本。
2. 先补齐第 3 节的分层计数器，不先改变通信行为。
3. 复现后保留现场，完成两端 UART+AUX 同步抓取。
4. 已知软件重启无效、模块单独掉电可恢复；下一步优先验证仅拉 RESET 能否恢复。
5. 测量故障前后模块电源、RESET、模式脚和 AUX，确认模块异常的硬件诱因。
6. 根据第 6 节判定具体故障层。
7. 再按第 7 节逐项修改，每改一项单独压力测试，避免无法归因。
